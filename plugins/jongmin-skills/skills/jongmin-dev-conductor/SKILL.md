# jongmin-dev-conductor — 다중 레인 개발 편성

지휘부(메인 세션)는 구현 코드를 직접 쓰지 않고 **스코프 확정·레인 배선·직접 검증·리뷰 접합**만 한다.
병렬성은 읽기 레인에서 얻고, 쓰기는 한 번에 하나만. 지휘 컨텍스트를 조율에만 쓰는 것이 이 편성의 핵심 가치다.

## 발동 게이트

**적합** (하나 이상 해당):
- 커밋 3건 이상이 예상되는 다중 파일 구현 웨이브
- 무손실 최적화·동작 보존 리팩토링 등 **등가성(오라클) 검증이 결과의 핵심**인 작업
- 회귀 비용이 큰 고위험 변경 (데이터 정합성, 수치 동일성, 마이그레이션)
- 사용자가 편성/교차검증을 명시적으로 요청

**부적합** (일반 진행으로):
- 단일 파일·소규모 수정, 일상적 멀티파일 리팩토링
- 프로토타입·일회성 스크립트 등 리뷰 독립성의 가치가 낮은 작업

판단 기준은 **저장소 크기가 아니라 "웨이브 규모 × 회귀 리스크"**다.
소형 프로젝트라도 데이터를 깨뜨리면 안 되는 변환 로직이면 적합하고,
대형 프로젝트라도 한 줄 수정이면 부적합하다.

## Preflight (발동 직후, 레인 발진 전)

복사해서 체크하며 진행:

```
- [ ] git 저장소 확인, 기준 SHA 기록: BASE=$(git rev-parse HEAD)
- [ ] 워킹트리 상태 확인 — 더티면 사용자에게 처리 방침 확인
- [ ] 커밋 권한 확인 — 이번 웨이브에서 에이전트가 커밋해도 되는지 사용자에게 1회 확인 (push는 항상 금지)
- [ ] codex 가용 확인: `codex login status` — 실패 시 읽기 레인을 Claude 반박 감사로 강등
- [ ] 프로젝트 규약 수집 — CLAUDE.md, 테스트 규약, 수치 표기 규약 등 에이전트 프롬프트에 복제할 목록 작성
```

## 편성

| 레인 | 바인딩 | 역할 | 제약 |
|---|---|---|---|
| 지휘 | 메인 세션 | 근거 수집, 프롬프트 작성, 착지 검증, 리뷰 접합, 최종 보고 | 구현 코드 직접 작성 금지 (검증 스크립트는 예외) |
| 쓰기 | Agent(`general-purpose`, `model: opus`) + [executor-prompt.md](executor-prompt.md) | 구현 + 테스트 + 커밋 | **한 번에 1개** — 같은 파일을 만지는 쓰기 레인 병렬 금지 |
| 읽기 | `codex exec` read-only — 실행 패턴은 [codex-lane.md](codex-lane.md) | 다음 작업 명세, 반박 지향 교차검증 | 쓰기와 파일 충돌 없음 → 상시 병렬 가능. `-m` 지정 금지 |
| 리뷰 | `lane-reviewer` 에이전트 (없으면 `general-purpose`에 read-only 지시) | 착지된 커밋 범위 독립 리뷰 | 자기승인 금지 — 지휘부·쓰기 레인이 리뷰를 대신하지 않는다 |

모델은 별칭/설정으로만 지정한다: 쓰기·리뷰는 `opus` 별칭, codex는 `~/.codex/config.toml` 기본값.
모델 ID를 이 스킬이나 프롬프트에 박지 않는다 — 모델 세대가 바뀌어도 스킬은 불변이어야 한다.

## 웨이브 진행

복사해서 체크하며 진행:

```
- [ ] 1. 근거 수집 (지휘부 직접)
- [ ] 2. 쓰기 레인 발진
- [ ] 3. 읽기 레인 병렬 발진
- [ ] 4. 착지 검증 (지휘부 직접, 생략 금지)
- [ ] 5. 리뷰 패스 (SHA 범위 지정)
- [ ] 6. 리뷰 접합
- [ ] 7. 최종 보고
```

**1. 근거 수집** — 대상 코드/문서를 직접 읽고, 가능하면 재현 실험으로 가설을 먼저 확증한다.
이 근거의 질이 executor 프롬프트의 질을 결정한다.

**2. 쓰기 레인 발진** — [executor-prompt.md](executor-prompt.md)의 5요소를 모두 채워 발진한다.
핵심은 **사양 이탈 보고 요구**다: executor가 사양의 결함을 실측으로 거부하는 것이
최선의 산출물일 수 있다.
> 함정: 에이전트는 세션 컨텍스트·프로젝트 메모리를 못 본다 — 필요한 규약은 전부 프롬프트에 복제하라.

**3. 읽기 레인 병렬 발진** — codex에 다음 작업의 명세 작성 또는 현재 가설의 반박 지향
교차검증을 맡긴다.
> 함정: 명세 시점 ≠ 착지 시점. 읽기 레인이 본 트리와 착지 후 트리가 다르면,
> 후속 executor 프롬프트에 그 차이(선행 커밋과의 합류 지점)를 명시하라.

**4. 착지 검증** — 완료 보고를 그대로 믿지 않는다: `git log`/`git status`로 커밋·클린 트리
확인 → 테스트 스위트 **직접 재실행** → 핵심 diff 직접 검토. 발견 사항은 다음 프롬프트에 반영한다.
> 함정: 서브에이전트 완료 통지는 완료가 아니다. 지휘부 직접 검증 전까지 완료 선언 금지.

**5. 리뷰 패스** — lane-reviewer에 `BASE..HEAD` **SHA 범위**와 집중 검증 축(논증의 구멍,
전제 성립 여부, 테스트 오라클의 실제 강도)을 지정해 호출한다. 범위가 SHA로 고정되므로
후속 쓰기 레인이 트리를 움직여도 리뷰는 영향받지 않는다.
> 함정: 리뷰어에게 HEAD나 워킹트리가 아니라 SHA 범위를 줘라.

**6. 리뷰 접합** — 지적사항은 쓰기 레인이 살아 있으면 그 레인에 접합한다(같은 파일을 만지는
시점이 접합 비용이 가장 싸다). 레인이 끝났으면 새 쓰기 레인으로 처리한다.

**7. 최종 보고** — 커밋 목록, 전후 지표, 리뷰 항목별 처리 결과, 다음 결정 지점.

## 실패·중단 정책

- 레인 실패: 서로 다른 접근 3회까지 시도 후 사용자에게 보고하고 중단
- 작업 범위 밖 파일 변경 감지 시 즉시 중단·보고
- 읽기 레인 무응답: 데드라인(기본 15분) 초과 시 잡 정지, 결과 없이 진행할지 판단
- 웨이브 중단 시 정리: 백그라운드 잡 정지, 생성한 worktree 제거, 현재 상태 보고

## 성공 기준

- 전 커밋 착지 + 지휘부 재실행 테스트 green + 클린 트리
- 리뷰 critical 0 (major는 접합 처리 완료)
- 문서 정합까지 같은 웨이브 내 완료
- push 없음 (사용자 명시 지시 전까지)

## 환경 노트

- OMC 설치 환경이면 쓰기=`oh-my-claudecode:executor`, 리뷰=`oh-my-claudecode:code-reviewer`로
  바인딩해도 된다. 편성 계약은 동일하다.
- 서로 다른 파일군에 대한 쓰기 레인 병렬화(worktree 격리)는 미검증 — 시도하면 결과를 이 스킬에 반영할 것.
