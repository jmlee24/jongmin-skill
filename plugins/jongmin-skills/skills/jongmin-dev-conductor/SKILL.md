# jongmin-dev-conductor — 다중 레인 개발 편성

정체성: **병렬 접합기**. 지휘부(메인 세션)는 구현 코드를 직접 쓰지 않고 **스코프 확정·레인
배선·직접 검증·리뷰 접합**만 한다. 핵심 성능은 리뷰 수가 아니라 **쓰기 1개 원칙을 유지하면서
검증·명세·리뷰를 겹치는 능력**이다. 병렬성은 읽기 레인에서 얻고, 쓰기는 한 번에 하나만.

쓰기 모드 3단계 (기본은 항상 1): ① `single-writer` (기본) ② `pipeline` (쓰기 1개 + 리뷰
병렬 — 웨이브 진행 절차가 이것) ③ `parallel-write` (실험 — 아래 실험 모드 절, 기본 비활성).

## 발동 게이트

**적합** (하나 이상 해당):
- 커밋 3건 이상이 예상되는 다중 파일 구현 웨이브
- 무손실 최적화·동작 보존 리팩토링 등 **등가성(오라클) 검증이 결과의 핵심**인 작업
- 회귀 비용이 큰 고위험 변경 (데이터 정합성, 수치 동일성, 마이그레이션)
- 사용자가 편성/교차검증을 명시적으로 요청

**부적합** (일반 진행으로):
- 단일 파일·소규모 수정, 일상적 멀티파일 리팩토링
- 프로토타입·일회성 스크립트 등 리뷰 독립성의 가치가 낮은 작업

판단 기준은 **저장소 크기가 아니라 "웨이브 규모 × 회귀 리스크"**다.
소형 프로젝트라도 데이터를 깨뜨리면 안 되는 변환 로직이면 적합하고,
대형 프로젝트라도 한 줄 수정이면 부적합하다.

## Preflight (발동 직후, 레인 발진 전)

복사해서 체크하며 진행:

```
- [ ] git 저장소 확인, 기준 SHA 기록: BASE=$(git rev-parse HEAD)
- [ ] 워킹트리 상태 확인 — 더티면 기존 변경 파일 목록을 장부에 기록해 executor 변경과 구분
- [ ] 발진 배치 질문 1콜 (question-policy.md) — 미확정 항목만 모아 AskUserQuestion 1회:
      커밋 권한(항상 포함), 더티 트리 처리 방침(더티일 때), 범위 경계·성공 기준(모호할 때).
      이후 런 중 질문 금지 — 유예 3분류(defer/gate/block)로 장부 기록, 종료 배치로 제시
- [ ] codex 가용 확인: `codex login status` — 실패 시 읽기 레인을 Claude 반박 감사로 강등
- [ ] 프로젝트 규약 수집 — CLAUDE.md, 테스트 규약, 수치 표기 규약 등 에이전트 프롬프트에 복제할 목록 작성
```

런 중 즉시 질문 예외는 question-policy.md의 4종(불가역·금지선 충돌·사용자 변경 덮어쓰기
위험·3접근 소진)뿐이다.

## 편성

| 레인 | 바인딩 | 역할 | 제약 |
|---|---|---|---|
| 지휘 (T1) | 메인 세션 | 근거 수집, 프롬프트 작성, 착지 검증, 리뷰 접합, 불일치 실측 판정, 최종 보고 | 구현 코드 직접 작성 금지 (검증 스크립트는 예외) |
| 쓰기 (T2) | Agent(`general-purpose`) + [executor-prompt.md](../../shared/executor-prompt.md) | 구현 + 테스트 + 커밋 | **한 번에 1개** — 같은 파일을 만지는 쓰기 레인 병렬 금지 |
| 읽기 (CX) | `codex exec` read-only — 실행 패턴은 [codex-lane.md](../../shared/codex-lane.md) | 다음 작업 명세 생성, 대안 제시, 반박 지향 교차검증 | 쓰기와 파일 충돌 없음 → 상시 병렬 가능. **소견은 자문** — 자동 반영 금지 |
| 리뷰 (T2) | `lane-reviewer` 에이전트 (없으면 `general-purpose`에 read-only 지시) | 착지된 커밋 범위 독립 리뷰 — 착지물 리뷰의 주도자 | 자기승인 금지 — 지휘부·쓰기 레인이 리뷰를 대신하지 않는다 |

티어 바인딩·승격 밸브·교차 리뷰 비대칭 규칙은 [model-tiers.md](../../shared/model-tiers.md)가
유일한 정의 지점이다. 모델 ID를 이 스킬이나 프롬프트에 박지 않는다.
리뷰(T2)와 읽기(CX)의 소견이 갈리면 지휘부(T1)가 실측으로 판정한다 — CX 지적은 반증 방법 없이 기각 금지.

## 웨이브 진행

**파이프라이닝 원칙**: 벽시계 시간의 주적은 T1의 동기 대기다. 쓰기 레인은 한 번에 1개(불변)지만,
리뷰·CX·다음 프롬프트 준비는 SHA 고정 뒤 전부 병렬이다. 직렬로 돌면 벽시계 ≈ 레인 시간의 합이 된다
(실측: 5시간 웨이브의 원인).

복사해서 체크하며 진행:

```
- [ ] 1. 근거 수집 (지휘부 직접)
- [ ] 2. 쓰기 레인 발진 — 백그라운드, 완료까지 동기 대기 금지
- [ ] 3. 병행: 읽기 레인 발진 + 다음 태스크 근거 수집·프롬프트 작성 (T1 유휴 금지)
- [ ] 4. 착지 검증 (완료 통지 후 지휘부 직접, 생략 금지) → 끝나면 즉시 다음 태스크의 2로
- [ ] 5. 리뷰 패스 (SHA 범위, 백그라운드) — 커밋 N 리뷰 ∥ 태스크 N+1 쓰기 (SHA 고정이 보장)
- [ ] 6. 리뷰 접합 — 결과 도착 시점에, 살아있는 쓰기 레인 우선
- [ ] 7. 최종 보고 — 전 리뷰 도착·접합 확인 + 시간 장부
```

**1. 근거 수집** — 대상 코드/문서를 직접 읽고, 가능하면 재현 실험으로 가설을 먼저 확증한다.
이 근거의 질이 executor 프롬프트의 질을 결정한다.

**2. 쓰기 레인 발진** — [executor-prompt.md](../../shared/executor-prompt.md)의 5요소를 모두 채워 발진한다
(채워진 실물 예시가 그 문서에 있다). T2가 프롬프트 개선 후 재시도로도 실패하면 승격 밸브 적용
([model-tiers.md](../../shared/model-tiers.md)).
핵심은 **사양 이탈 보고 요구**다: executor가 사양의 결함을 실측으로 거부하는 것이
최선의 산출물일 수 있다.
> 함정: 에이전트는 세션 컨텍스트·프로젝트 메모리를 못 본다 — 필요한 규약은 전부 프롬프트에 복제하라.

**3. 읽기 레인 병렬 발진** — CX는 **상시 2슬롯 병렬**이 기본이다 (스레드 분리):
- CX-A: 다음 태스크 명세 생성
- CX-B: 방금 착지물 adversarial 반박
- 고위험·등가성 작업이면 CX-C(아키텍처·인터페이스 충돌 전용) 추가 — 상한은 접합 큐 규칙
  ([codex-lane.md](../../shared/codex-lane.md) 발진 상한)이 결정한다. 산출은 전부 Top 5 형식.

CX의 강점 배치는 생성·반박이다 — 착지물의 최종 리뷰는 리뷰 레인(T2)이 주도한다.
**선행 스킬 산출물 인정**: 같은 작업에 대해 warplan(계획 반박)·deep-audit(감사)이 이미 CX 산출물을
만들었다면 재발진 없이 읽기 레인 입력으로 쓴다 — 단, 자동 채택 금지는 동일하고, 산출 시점의
기준 SHA와 현재 트리의 차이를 확인해 후속 executor 프롬프트에 합류 지점을 명시한다.
> 함정: 명세 시점 ≠ 착지 시점. 읽기 레인이 본 트리와 착지 후 트리가 다르면,
> 후속 executor 프롬프트에 그 차이(선행 커밋과의 합류 지점)를 명시하라.

**4. 착지 검증** — 완료 보고를 그대로 믿지 않는다: `git log`/`git status`로 커밋·클린 트리
확인 → 테스트 스위트 **직접 재실행** → 핵심 diff 직접 검토. 발견 사항은 다음 프롬프트에 반영한다.
> 함정: 서브에이전트 완료 통지는 완료가 아니다. 지휘부 직접 검증 전까지 완료 선언 금지.

**5. 리뷰 패스** — 착지 직후 읽기 레인을 **병렬 발진**한다 (전부 SHA 범위 고정, 백그라운드):
- **quick 리뷰**: 차단 이슈(critical)만 신속 탐지 — 다음 쓰기 진행 여부는 이것만 보고 판정
- **deep 리뷰**: `lane-reviewer` 전면 리뷰, 집중 축 지정(논증의 구멍, 전제 성립, 오라클 강도)
- **CX adversarial**: 고위험·등가성·오라클 작업에서 반박 레인 추가

상한: 읽기 레인 총 3개 기본(예외 4개), 커밋별 deep 리뷰 동시 2개까지 — 그 이상은 중복 지적과
접합 순서 꼬임으로 이득이 준다. **판정 큐는 T1 하나**: 중복 지적은 T1이 병합. 접합 시점은
심각도로 고정한다 — **critical 즉시 중단·접합 / major는 같은 파일을 만지는 다음 쓰기 발진 전
접합 필수 / minor·nit는 종료 게이트 묶음**. 접합 전 freshness rule(codex-lane.md)로 리뷰
기준 SHA와 현재 HEAD의 overlap을 확인 — stale 리뷰는 자동 접합 금지.
> 함정: 리뷰어에게 HEAD나 워킹트리가 아니라 SHA 범위를 줘라. executor 자기 보고 공유 금지.
> 함정: 접합이 진짜 병목이다 (wave2 실측: 꼬리 9분). 리뷰 도착 즉시 접합 프롬프트를 준비해두라.

**6. 리뷰 접합** — 지적사항은 쓰기 레인이 살아 있으면 그 레인에 접합한다(같은 파일을 만지는
시점이 접합 비용이 가장 싸다). 레인이 끝났으면 새 쓰기 레인으로 처리한다.

**7. 최종 보고** — 커밋 목록, 전후 지표, 리뷰 항목별 처리 결과, 다음 결정 지점,
**시간 장부**(레인별 시작/종료/대기 — [ledger.md](../../shared/ledger.md) 3절. 다음 웨이브의
병목 튜닝은 추정이 아니라 이 실측으로 한다). 유예 결정이 있으면 종료 배치 1세트로 제시
(question-policy.md).

## 실패·중단 정책

- 레인 실패: 서로 다른 접근 3회까지 시도 후 사용자에게 보고하고 중단
- 작업 범위 밖 파일 변경 감지 시 즉시 중단·보고
- 읽기 레인 무응답: 데드라인(기본 15분) 초과 시 잡 정지, 결과 없이 진행할지 판단
- 웨이브 중단 시 정리: 백그라운드 잡 정지, 생성한 worktree 제거, 현재 상태 보고
- **컴팩션 임박·세션 경계**(계정 전환, 기기 이동): `handoff` 스킬로 스냅샷을 뜬 뒤 중단한다 —
  재개는 handoff restore가 담당

## 성공 기준

- 전 커밋 착지 + 지휘부 재실행 테스트 green + 클린 트리 (결정론 게이트 포함 — landing-check.md)
- 리뷰 critical 0 (major는 접합 처리 완료)
- **회귀 가드 (조건부)**: 이 웨이브가 deep-audit CONFIRMED major/critical 구조 결함을 고치는
  웨이브면, 재발 방지 가드(테스트·타입 제약·린트 규칙 중 가장 싼 층)를 **같은 웨이브에서 착지**한다.
  가드는 "수정 전 실패 → 수정 후 통과"를 증명해야 하며(불가능하면 사유 보고), 문자열 매칭보다
  구조적 검사를 우선하고, 가드 자체도 리뷰 대상에 포함한다. 새 도구 설치 금지.
- 문서 정합까지 같은 웨이브 내 완료
- push 없음 (사용자 명시 지시 전까지)

## 실험 모드: contract-isolated write lanes (기본 비활성)

"인터페이스가 명확하면 쓰기 병렬이 안전하다"는 직관은 조건부로만 맞다 — 실제 실패 원인은
인터페이스가 아니라 **숨은 결합**(전역 상태·import 사이클·shared fixture/mock·config/env·
마이그레이션 순서·생성 파일·lockfile·snapshot·포맷터 대량 diff)이다. 활성 조건 전부 충족 시에만:

```
- [ ] 사용자 명시 요청 또는 T1의 실험 모드 선언 (장부 기록)
- [ ] 계약 동결 커밋 선행 — 시그니처·스키마·공용 타입을 먼저 착지하고 SHA 기록
- [ ] 파일 소유권 disjoint 맵 — 레인별 Owned/Forbidden 목록 (공용 타입·픽스처·config는 전 레인 Forbidden)
- [ ] 레인별 worktree 격리, executor 프롬프트에 6요소(소유권·계약 — executor-prompt.md) 필수
- [ ] 통합 커밋은 T1이 직렬 수행, merge order 명시, 통합 후 전체 스위트 재실행 + contract drift 확인
      (공개 API diff·스키마·생성물·lockfile·픽스처 변경 여부)
```

실패 시 폴백: 전 병렬 쓰기 중단 → 산출 diff는 patch 후보로만 보존 → single-writer로 재계획.
계약 위반·소유권 밖 수정 감지 즉시 발동한다. 최대 2~3레인, 작은 독립 모듈에서만.
