# 근거 생존성 검증 — 인용한 코드·문서가 살아 있는가

계획·편성·재개의 전제가 되는 인용(파일:라인·함수·설정·문서 조항)은 **실존할 뿐 아니라
살아 있어야** 한다. 실측: 존재하지 않는 파일 2개를 소유권 맵에 배정, 이름이 비슷한 다른 큐의
수치를 인용 — 둘 다 "확인 안 하고 인용"이 원인이었고, 계획 단계에서 같은 일이 나면 웨이브
전체가 틀린 전제 위에 선다.

codex-lane의 freshness rule은 **리뷰 산출물의 시점** 신선도이고,
이 절차는 **인용 대상 자체의** 생존성이다 — 다른 검사다.

## 검증 층

| 층 | 내용 | 담당 |
|---|---|---|
| 기계 검증 | 기준 SHA 실존, `git show <SHA>:<path>` 실존, 인용 줄·심볼·문서 제목 실존 | T1 필수 (grep·git) |
| 트리 구분 | HEAD 근거와 미커밋 워킹트리 근거를 섞지 않고 별도 표기 | T1 필수 |
| 실행 생존성 | 엔트리포인트에서 실제 호출되는가 — import·등록·설정·feature flag가 연결돼 있는가 | T1 판정 + CX 반박 |
| 코드 성격 | production / test-only / generated / legacy / dead / unreachable | T1 판정 + CX 반박 |
| 문서 현행성 | 권위 문서인가, 코드·설정과 충돌하지 않는가, 폐기된 설계가 아닌가 | T1 판정 + CX 반박 |

결과는 인용마다 **`LIVE / STALE / DEAD / UNVERIFIED`** 중 하나로 T1이 확정한다.

## 규칙

- **`LIVE`만 계획의 확정 전제로 쓴다.** 나머지는 가정·위험·유예 결정으로 내린다 — 죽은 코드를
  실행 근거로, stale 문서를 현행 사양으로 인용한 계획은 컴파일되지 않은 계획이다.
- 파일:라인이 존재한다는 사실은 그 주장이 참이라는 증명이 아니다. `rg` 참조 개수·최근 수정일도
  단서이지 생존 증명이 아니다.
- CX 반박 프롬프트에 필수 축으로 넣는다: "핵심 전제의 인용을 재확인하고, 죽은 코드·stale
  문서·주석을 실행 근거로 오인한 곳을 찾아라." CX 산출에는 근거 기준 SHA + 상태를 요구한다.
- executor에게 전달한 근거가 `STALE/DEAD`로 판명되거나 기준 SHA와 어긋나면, executor는
  구현을 멈추고 실측 반박한다 (executor-prompt.md 사양 이탈 조항).

## 적용 지점

warplan 근거 수집 / conductor 근거 수집·DAG 편성 / deep-audit 의심 카탈로그 /
handoff restore("다음 단계"를 결정하는 주장) — 각 스킬은 적용 지점만 명시하고 절차는 여기를 참조한다.
